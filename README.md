# 命式エンジン

四柱推命の命式を、天文計算から立てる。GitHub Pages で動く静的サイト。

`index.html` を開けば動く。ビルドステップは無い。

## 天盤

画面の中心は、実データで描いた同心円の盤。羅盤の形は借りたが、判断は借りていない。
描いてあるものは全て engine が計算した値である。

- **外環** — 十二節を実際の黄経に置き、立春を天頂に取ってアンラップした環。
  月支の判定に使っている座標そのもの
- **太陽** — 出生時の太陽視黄経
- **内環** — その土地の一日の十二時辰
- **二本の針** — 標準時と真太陽時。**その角度差が27分そのもの**で、
  説明ではなく図形として出る
- **朱の弧** — 誤差棒
- **中心** — 日主

飾りは足していない。逆に、不確かなものを確からしく見せる装飾もしていない。

### 環は読める

環に触れる（またはキーボードでフォーカスする）と、その節の節入り時刻と、
その時辰の時間帯が出る。出るのは全て下の表にもある値で、
**触らないと読めない情報は一つも無い。**

## 読み（Phase 4）

**盤の要素に紐づかない文は、一文も出さない。** 誰にでも当てはまる文を個人向けの
顔で出すことが、このアプリにおける唯一の嘘であり、事実誤りより優先度が高い。

これを気合いではなく構造で守っている。

- 各文は空でない `source` 配列を必ず持つ
- `source` が空の文は **UIで隠すのではなく `readChart` の生成段階で捨てる**
- 出典は画面に出す。読者が全文を盤と突き合わせて検算できる
- 引用された文字が本当に盤にあるかを検算で強制している（架空の引用を防ぐ）

モデルは呼んでいない。全てページ内で計算するので、生年月日も座標も端末から
出ないままで、APIキーも要らない。

蔵干・通変星・十二運は v1 対象外なので、どの規則もそれらに依存していない。
そして**人物についての記述は一切しない** — 書くのは盤の配置についてだけ。

### 反バーナムの計測

```
node tools/reading-metrics.mjs 20000
```

ランダムな命式20,000件で:

| 指標 | 盤の読み | 場面ごとの箇条書き |
|---|---|---|
| 被覆率 | 100.0% | 100.0% |
| 組み合わせ数（異なる読みが何通り作れるか） | 19,354 | 19,350 |
| 上限到達率（異なる命式 19,354 に対して） | **100.0%** | **100.0%** |
| 最頻共有率 | 0.0%（最多で3人が共有） | 0.0%（同上） |
| 出典の無い文 | 0 | 0 |

**この表は一度書き直している。** 前は 7,689通りと書いてあった。数えかたを変えた
わけではなく、**標本抽出器が壊れていたので、2万件の抽出が7,689種類の命式にしか
ならなかった**（下の「精査で見つけて直したもの」を参照）。直したいまは 19,354種類で、
到達率が 100% であることは変わらない。

組み合わせを `source` で測るのは、言い換えによる水増しを防ぐため。生テキストで
測ると、同じ主張を書き直しただけで数字が上がってしまう。

**以前ここに書いていた「弁別率 96.1%」は取り下げた。** 定義が
`組み合わせ数 ÷ 標本数` だったので、**標本を増やすと必ず下がる**。同じエンジン・
同じ規則で、標本1,000なら46.2%、4万なら2.4%。あれは品質ではなく標本サイズの
指標だった。いま出しているのは飽和する量——**組み合わせ数**（標本を4万にしても
動かない）と、**上限（異なる命式の数）に対する到達率**。

### 材料を4つから9つに増やした（新しい計算は0行）

この計測が、いちばん効く改善を教えてくれた。箇条書きは
**用神・欠け・判定・通根の4つ**しか見ておらず、上限到達率は **19.8%**——
異なる読みが **978通り**しか作れない飽和状態だった（標本を4万に増やしても増えない）。
千人が使えば、必ず同じ助言を受け取る二人が出る。

足りなかったのは新機能ではなく**配線**で、エンジンは既に全部を計算していた:

| 足した材料 | どこから来るか |
|---|---|
| 宮（月支・日支・時支） | 各柱の支と日主の五行関係。伝統的な担当は 月支＝社会・仕事、日支＝いちばん近い人、時支＝晩年と体 |
| 最多五行 | `elementBalance` の最大値。お金の欄が読む |
| 大運の追い風/向かい風 | `luckPeriods` ＋ `cycleAtAge`。いま立っている10年 |

結果は **978 → 4,026通り、到達率 19.8% → 92.7%**。`pillars.js` にも `strength.js` にも
触っていない。

支は12通りあるが、**五行の関係（比和・生我・我生・我剋・剋我）の5通りで引いている**。
12×4場面＝48行を急いで書くより、5×4＝20行を練って書くほうが良い文章になるため。

**この節の数字（978 → 4,026、19.8% → 92.7%、12通りなら96.2%）は、壊れた標本抽出器で
測ったものである。** 当時のコードはもう無いので測り直せない。取り下げずに残すのは、
どういう判断でこの配線を足したかの記録だからで、**いま有効な数字は上の表**
（19,354通り・到達率100%）のほうである。比の向き——配線を足すと桁で増える——は
残るが、桁そのものは信用しないこと。

## 通変星（十神）

四柱推命の解釈が実際に喋られている語彙。ここまでは全部「五行」の粒度
——「土が要る」「月支が削る」——で止まっていた。正しいが粗い。伝統はそこで止まらず、
日主から見た**関係のほうに名前を付ける**。財＝お金と扱えるもの、官＝立場と自分を律する
もの、印＝支えと学び、食傷＝外に出すもの、比劫＝対等な相手。

読者の生活にそのまま重なるのが、入れる理由。

| | 日主を | 陰陽 | |
|---|---|---|---|
| 比肩 / 劫財 | 同じ五行 | 同 / 異 | 対等な相手 |
| 食神 / 傷官 | 日主が生む | 同 / 異 | 外に出すもの |
| 偏財 / 正財 | 日主が剋す | 同 / 異 | お金と、扱えるもの |
| 偏官 / 正官 | 日主を剋す | 同 / 異 | 立場と、自分を律するもの |
| 偏印 / 印綬 | 日主を生む | 同 / 異 | 支えと、学ぶこと |

**表を写していない。** 十神は「五行の関係 × 陰陽の同異」から機械的に落ちるので、
書き写す表が無い。検算も**構造**で行う——本から写した表を照合しても、写し間違いが
無いことしか分からないため:

- どの日主から見ても、10種が過不足なく1回ずつ対応する（100通り）
- 比肩は日主と同じ干のときだけ立つ
- 陰陽の同異が「偏」と「正」の側をそのまま決める
- **逆から見ると必ず対になる**——BがAの正官なら、AはBの正財。剋我を逆から見れば我剋
  だから。生剋の向きをどこかで取り違えていれば、これが破れる
- 加えて、どの本にも載っている甲の行だけは1文字ずつ照合する

**弁別のためではなく語彙のために入れた**——と書くつもりだったが、実測では到達率が
92.7% → 100.0% に上がった。見立ては半分外れている。ただし主眼は今も語彙のほうで、
「仕事」「お金」の欄が五行を経由せずに、その欄が本当に扱っている星を直接見にいける
ようになったことが本体。

**入れていないもの**: 格局（建禄格・食神格…）。流派差が大きく、81画の吉凶表を
落としたのと同じ理由で、測れる地面が無い。

**計測だけで、最適化ループは実装していない。** 正解の無い領域に最適化を掛けると
代理指標は必ず「読んで気持ちいいか」に落ち、自己改善する占い師はバーナム機械に
収束するため。

## 結論を出す — 身強・身弱と用神

四柱推命の鑑定は**判定**に集約される。日主がどれだけ強く立っているか（身強／身弱）、
そこから**その人に必要な五行＝用神**が決まる。ここが無いと、正しい観察が
並ぶだけで何も伝わらない。最初の実装はそれをやっていた。

- 扶抑法。月令を3倍、残る七字を1倍で足し引きし、地支に日主と同じ五行があれば
  通根として +1。±1 の内は中庸
- **点数と内訳を必ず出す。** ラベルだけでなく、境界からどれだけ離れているかも出す。
  近ければ「流派や蔵干の扱いで逆に振れうる」と書く
- 蔵干は入れたが、**流派を選ばず両方計算して割れたら明示する**（下記）
- 重みは定数として並べてある。流派の違いは、その定数を指して議論できる

## 一目で分かる層 — 「微妙でわかりづらい」への答え

作者から「なんか全体的に微妙だしわかりづらい」と言われた。正しい指摘だった。

計算は合っていて、出典も全文に付いていて、頻度も測ってある。それでも
**4ページとも「読ませる」作りで、一目で分かる層が一つも無かった。**
どのページもフォーム → 注意書き → 段落で始まる。開いて3秒で「で、何なの」が掴めない。

そこで世の中の占いを調べて、**こちらに一つも無かった伝え方**を4つ取り込んだ。

| 借りたもの | どこの | 効いている理由 |
|---|---|---|
| **形容詞＋名詞** | 動物占い（「長距離ランナーのチータ」） | 声に出して言える。こちらは「夏の宝石」と名詞だけで、しかもページ中ほどに埋もれていた |
| **区分に畳む** | 六星占術（12運気を4区分に） | こちらの大運帯は**90マスあって区分が無かった** |
| **今日の一言＋やること/避けること** | 日々の占い全般 | 行動に落ちている |
| **吉方位** | 九星気学 | 方位は**動ける**。本命星は既に出していた |

**新しい占い規則は0行。** 全部、既に計算済みの値の**並べ替えと大きさ**である。
出典も他と同じで、全文が非空の `source[]` を持つ。

### 置き場所は均等ではない

**盤ページには置かなかった。** このページは自分の憲法で
「**人物についての記述は一切しない** — 書くのは盤の配置についてだけ」と宣言している。
「積み上げて強くなる — 夏の宝石」も ◎○△ も人物評なので、置けば
**このリポジトリ最大の自己矛盾**になる。置かない判断のほうを、ブラウザ監査に
回帰テストとして入れてある（盤に `.hero-phrase` や `.mark-row` が出たら落ちる）。

| ページ | 置いたもの |
|---|---|
| 語り | 4つ全部、出力の最上部 |
| 託宣 | 一言だけ（「名指してから告げる」は託宣の作法なので声が壊れない。◎○△ の表は壊す） |
| 重ね | 吉方位だけ（導出元の九星気学カードの中） |
| 盤 | **何も置かない** |

### ◎○△ は絶対評価をやめた（実測で分かった）

最初は各場面の五行が用神か忌神かで ◎○△ を付けた。素直だが**実測が壊れていた**:

```
work    △ 76%  ○ 10%  ◎ 15%
最頻の並び  △△△△  16.2%
```

身弱の盤は5つの五行のうち3つを忌神にするので、**△ が構造的に多数派になる**。
これは場面を説明しておらず、判定の形を説明している。しかも4人に3人が
「あなたの仕事は手がいる」と言われる——不正確なうえに失礼である。

**4つを互いに比べる**ように直した。◎は「あなたの4つの中でいちばん風が味方している場面」。
これで分布が割れ、しかも主張として正確になる（読者はもともと記号表をそう読む）。
4つとも同点なら全部○にする——順位が付かないときに順位を作らない。

```
work    △ 47%  ○ 30%  ◎ 23%
最頻の並び  ○○○○  16.4%   ← 「4つとも横並び」という正直な答え
```

検算に「どの場面のどの記号も過半に達しない」を入れた。最初の版ならこれで落ちる。

### 時期 — 90マスを名前の付いた数本に

大運の `fit` が同じ区間をつなげて名前を付ける。**伸ばす期／整える期／守る期**、
それに立運前の**大運前**。

**4つに揃えていない。** 揃えるには規則の無いところに境界を1本発明することになる。
借りたのは*畳むこと*であって数ではない。名前も六星占術のもの（上昇期・大殺界など）は
使わない——他所の商標的な語彙は借りない。

帯（90マス）は消していない。下にそのまま残っている。

### 頻度キーで3回目の同じバグを出した

「伸ばす期」も「守る期」も**実測100%**で出た。90年もあれば誰でも両方を通るからで、
これは真だが無内容である。**キーが主張ではなく命式を識別していた**——このリポジトリで
3回目の同じ間違い。ページが実際に言うのは「**いまは**【守る期】」なので、
キーも「いま立っている期」に直した。

一言も同じ扱いにした。表示は「形容詞句 — 型名」の一行なので、**キーも一行ぶん**にする。
形容詞だけを測ると「4人に1人」が型名まで含んだ文の横に出て、
主張の半分にしか掛かっていない数字が全体に掛かって見える。

### 吉方位（`app/engine/compass.js`）

このアプリが出すものの中で**唯一その日に動けるもの**。九星気学の年盤から出す。

年盤は洛書の魔方陣を、その年の中宮星ぶん回すだけ:

```
星(方位) = ((基本星(方位) - 1 + (中宮星 - 5)) mod 9) + 1
```

**公表値で裏が取れる。** 2026年は中宮が一白なので、この式だと五黄が南に来て、
その対冲の暗剣殺が北に来る。複数の九星気学の資料が「2026年の五黄殺は南、暗剣殺は北」と
書いている。回転を1つ間違えていたら当たらない。検算に入れてある。

採った規則も書いてある——万人共通の凶（五黄殺・暗剣殺・歳破）、本人の凶（本命殺・本命的殺）、
吉は残りのうち本命星と相生の星がいる方位。**五黄は誰の吉にもならない**（唯一どの流派も
一致する例外）。月盤は見ていないので、**そう書いてある**。

## 語り（別ページ・voice.html）

**盤のページが自分に禁じているものを、あえて置いた別ページ。** 人物評・助言・
年運がある。

構成は **走り読みできる順序**に従う:
**名前 → 命式 → 目盛り4本 → 強み・つまずき・今すぐ → 場面ごと → 時の流れ → 長文**

### 読めるようにする — MBTI の結果画面から

最初の版は長い文章を9つ縦に積んでいた。「結局なにを言われたのか」を掴むには
全部読むしかない。MBTI の結果画面が分かりやすいのは名前や4文字コードのせいでは
なく、**①軸ごとの％バーで自分の位置が一目で分かる**ことと、**②「強み」「仕事」
などの固定見出しに短い箇条書きが入っていて、知りたいところに直行できる**ことだ。

移したのはその2点だけで、**占いの計算結果は一切変えていない**。4文字コードや
16タイプ名は作っていない——聞かれたのは伝え方であって、名前の付け方ではない。

**目盛り4本**（`app/engine/gauges.js`）。新しい判断は足さず、既に計算済みの値を
位置として見せる。`percent` は常に「左のラベル側へどれだけ寄っているか」で統一し、
色は**寄っている側の端から**塗る。左から塗ると、身弱の盤で「力が余る」側に色が
伸びて、絵と文字が逆のことを言う。

| 目盛り | 左 ↔ 右 | ％の定義 | 実測（2万件） |
|---|---|---|---|
| 出し方 | 外に出す ↔ 内にためる | 8文字のうち陽の割合 | 中央値 50%、4対4 が 40% |
| 力の余り | 力が余る ↔ 削られる | 扶抑法のスコア（±8でクランプ、中庸帯を帯で描く） | 5〜95%分位 −4.9〜+5.0 |
| かたより | 一点集中 ↔ まんべんなく | 最多五行 ÷ 8 | 4つ以上=30.3%、3つ=54.8% |
| 土台 | 土台がある ↔ 身軽 | 通根した地支 ÷ 4（蔵干込み） | 0本10% 1本29% 2本31% 3本22% 4本8% |

**流派で反転する目盛りには、その盤で印を出す。** 蔵干を数えるかどうかで
「力の余り」は **13.8%** の盤が左右反転し、「土台」は **28.7%** が反転する
（実測）。時刻の誤差棒が日柱をまたぐときは、日主に載っている2本が暫定であることも
出す。§2.5 が時刻にしている扱いと同じで、片方の流派の答えを唯一の答えとして
出さない。

**場面ごとの箇条書き**（`app/engine/domains.js`）。エンジンの結論は
「削られる側、金に寄れ」——正しくて出典もあるが、転職を迷っている人には使えない。
**用神・欠け・判定・通根**の4つを、仕事／人づきあい・恋愛／お金／心と体に
投影する。新しい占い規則は作っていない。1セクション3件まで、優先順位で決定論的に
選ぶ（乱数もローテーションも使わない）。

**長い文章は消していない。** 各セクションの「もっと読む」の中に畳んだだけで、
`plainwords.js` の言い回しはそのまま生きている。

### 型に名前を付ける

天星術が機能するのは、読み手が「私は満月」と言って帰れるからだ。四柱推命は
素材をすでに持っている——**十干の象**（甲＝大樹、辛＝珠玉、壬＝大海…）と
**月支の季節**。掛け合わせると40通りの型名になり、全て盤から導出される。

> 夏の珠玉 ／ 冬の大樹 ／ 秋の灯火

### 言葉を今の日本語にする

最初の版は文体が古かった。「無理が利かないのではなく、無理の利かせ方が違う」
——かっこつけているだけで伝わらない。専門語も画面に出しっぱなしだった。
四柱推命の本を一度も開いたことがない人には、何を言われているのか分からない。

全ての表示テキストを `app/engine/plainwords.js` に集約し、一つの規則で書き直した。
**友達に説明するように書く。**

- 二人称、です・ます、短い文
- 専門語は先に出さない。小さく後ろに添えるだけ
- 抽象を必ず具体に着地させる。「所属」ではなく「会社でも家でも、続けている習慣でもいい」
- 体言止め・文語・箴言を使わない

| 元 | 今 |
|---|---|
| 日主 | あなたの本体 |
| 身弱 | エネルギー控えめ型 |
| 用神 | 効くこと |
| 相生／相剋 | 助ける／削る |
| およそ42件に1件 | 42人に1人 |

### 「統計に基づく」を実際にやる

この種の占いは「統計学に基づく」と謳うが、数字はまず出てこない。
こちらは出す。**型名を含む全ての一節に、20,000件の実測頻度が付く**。
「およそ42件に1件」——当たっていると感じたとき、それが何人に当たる文なのかが
その場で分かる。

分けたことが正直さの本体である。盤のページでは全文が八字と突き合わせて検算でき、
出典の無い文は生成段階で捨てられる。語りのページは語り口が変わり、
**そのことをページ自身が冒頭で言う**。同じ重さで受け取られないために。

それでもバーナム機械にしないための縛り:

- 全ての一節が特定の文字に紐づき、出典を持つ（誰にでも当てはまる文にならない）
- 十干の象（甲＝大樹、辛＝珠玉、壬＝大海…）は伝統の受け売りで、当方の創作ではない
- **各節に「およそN件に1件」を付ける。** 当たっていると感じたとき、その配置が
  3件に1件なら、同じ文は世の中の3分の1に当たっている
- 同じ検算を語りにも掛けている（出典の有無・引用文字が盤にあるか・珍しさの実測値があるか）

**実測がバーナム文を1件捕まえた。** 「土台があるので、続けたものが実力として
残ります」は 通根の有無（あり／なし）に載せていたが、通根は **90.1%** の盤で
「あり」になる。ほぼ全員に当たる文をお世辞として出していたわけで、
`tools/reading-metrics.mjs` がそれを 70% 超として弾き出した。同じ事実を
**本数**（0〜4本、10/28/33/21/8%）に載せ替えて解決した。境目は2本で、
盤を 62% / 38% に割る。

年運は立春で切り替える。1月1日ではない。

## 託宣（別ページ・oracle.html）

**同じ盤、同じ計算、違う口調。** 三ページ目。

外から精査を受けて、こう指摘された——このアプリは曖昧さを許さない設計を
徹底した結果、**占いとして響かなくなっている**。「〜の傾向があります」
「あくまで一つの見方です」と数行おきに退避すると、読む側は最後まで
何も言われていない。誠実さのつもりが、実際には**どちらにも転べる書き方**を
選んでいるだけだった、と。

これは当たっている。ただし直し方は二つある。**盤と語りを曖昧にする**か、
**言い切るページを別に立てる**か。前者は既にあるものを壊すので、後者にした。

託宣ページの規則は一行で書ける:

> **変えるのは声だけ。事実は変えない。**

- ためらいの言葉を**各行から外し、入口に一度だけ置いた**。数行おきの
  ヘッジは誠実さではなく、両張りである。一度言って、あとは言い切る
- **作り話はしない。** どの一行も八字に紐づく。他の2ページと同じく
  全文が非空の `source[]` を持ち、空なら生成段階で捨てる
- **同じ生まれは何度でも同じことを言う。** 乱数は入っていない（検算あり）
- 根拠は消さずに**最後にまとめて畳んである**。数字で確かめたくなったら語りへ、
  という導線をページの入口に書いてある

命令形を使う（「土を踏め。」）。これは口調であって、新しい主張ではない——
同じ `用神` から、語りページは「土を増やすと楽になります」を出す。

## 重ね（別ページ・layers.html）— 系統を重ねても当たらない、を測って出す

「もっと色んな種類の占いを統合して、この世にまだないレベルの占いアプリを作りたい」への回答。
四柱推命に加えて**九星気学・宿曜・西洋占星術の三点・数秘術**を同じ生まれに当てる。

ただし——**系統を増やしても的中率は上がらない。** 上がるのは「当たっている感じ」のほうで、
これはこのアプリが最初から敵にしているものそのものである。5系統は5倍の文を出し、
そのうち何本かは韻を踏み、意味は読者が供給する。

なので**一致を見つけたら必ず、それが偶然どれくらい起きるかを横に置く。**
しかも「実測」だけでは足りない。20.7% と言われたら人は感心する。並べるべきは
**「もし2つが無関係ならどうなるか」**で、これは各系統が各々の答えを出す頻度から計算できる。

2万件で測った9組が、これ:

| 組み合わせ | 実測 | 無関係なら | 倍率 |
|---|---|---|---|
| 用神 × 本命星 | 20.7% | 20.8% | **1.00倍** |
| 用神 × 月命星 | 23.0% | 21.0% | 1.09倍 |
| 最多五行 × 本命星 | 18.7% | 22.7% | 0.82倍 |
| 最多五行 × 月命星 | 17.4% | 22.9% | 0.76倍 |
| 八字の陰陽 × 太陽星座の極性 | 51.8% | 50.0% | 1.04倍 |
| 八字の陰陽 × 月星座の極性 | 49.2% | 50.0% | 0.98倍 |
| 八字の陰陽 × ライフパスの奇偶 | 50.0% | 50.3% | 0.99倍 |
| 太陽星座の極性 × ライフパスの奇偶 | 49.7% | 49.6% | 1.00倍 |
| 月星座の極性 × ライフパスの奇偶 | 50.2% | 50.2% | 1.00倍 |

**どの2系統も、偶然を超えて一致していない。** 倍率は 0.76〜1.09 に収まる。

いちばん厳しい行は最後の3つである。**書いた日付の数字を足しただけの数秘術が、
西洋占星術と同じ程度に四柱推命と一致する。** 数秘術を入れたのはこのためで——
薄い系統を1本混ぜておくと、厚い系統どうしの一致がそれを超えるかどうかが測れる。
超えなかった。

これが「まだ無い」部分だと思っている。系統を重ねるアプリは多いが、
**重ねた結果を測って「意味がありません」と出すもの**は見当たらない。

### 比べてよいもの・いけないもの

- **五行は共有できる。** 九星は木火土金水を、命式と同じ相生相剋つきで持つ
- **西洋の四元素は共有できない。** 火・地・風・水は4つで、生剋の環を持たない。
  `west:fire` と `火` は翻訳の上でだけ同語なので、`western.js` は値に接頭辞を付けて
  **うっかり比較したら一致せずに落ちる**ようにしてある
- **陰陽と星座の極性は「同じ概念」ではない。** 二つの伝統が別々に、
  外向き/内向きに人を仕分けている。同じ側に落ちるかを問うのは正当で、
  **正当な理由は、そのあと偶然率を測るから**である。答えが半々なら偶然だと書く

### 宿曜は何とも比べられない（これも結果）

27のサイデリアル分割と12のトロピカル星座は、「同じかどうか」を問える相手ではない。
宿に五行を割り当てれば比較できるが、それは**このファイルが冒頭で禁じている
でっちあげの橋**そのもの（伝統が宿に付けるのは七曜と三性であって木火土金水ではない）。

検算がこれを捕まえた。「宿曜と西洋の月星座は独立でない」という印を書いたのに、
**その組は存在しなかった**。宿曜は単独で立っている。欠落ではなく、これも一つの結果である。

### 各系統について

**九星気学** — 新しい天文計算は0行。要るのは**立春で数えた年**と**節入りで数えた月**だけで、
エンジンが既に秒単位で出している。入れる価値があるのはまさにそこで、
多くの九星ツールは年を暦から取るため、**1月〜2月初旬生まれ全員に違う星を割り当てる**。
規則は表ではなく算術として書き、検算も性質で行う——本命星は599年ぶん毎年きっかり1つ下り、
月命星は2,400節月ぶん、立春をまたいでも1つずつ下る。3群×12ヶ月の表は、この下りの位相にすぎない。
位相は公表された年で留めてある（**2022年＝五黄土星**）。

**宿曜27宿** — 月は約22時間で1宿を通る。だから**記録が宿を決めないことは珍しくない**。
実測で、**±30分の記録は 4.9%、時刻の無い記録は 95.2% が2宿にまたがる**。
旧暦の表から引くツールはこれを言えず、どちらか一方を答える。ここは境界時刻を出して、
`uncertainty.js` が節入りにしているのと同じ自然頻度で「幅のうち2分の1」と書く。
分類器と境界探索は**同じサイデリアル定義**の上で走るので食い違えない。
独立確認として `swe_mooncross_ut` をトロピカル側から当てて36秒で一致する。

**西洋の三点** — 太陽は日付で決まり、月はおおよその時刻が要り、
アセンダントは**正確な時刻と緯度**が要る。この差そのものが、いちばん有用な情報だった。

> **時刻が無ければ、アセンダントを出さない。** 既定値でも「たぶん」でもなく、出さない。

一日で十二星座が昇るので、時刻の無い記録から出したアセンダントは12分の1の当てずっぽうである。
そこを埋めるのは占星術ソフトが最もよくやる正当化できない振る舞いで、
しかも**出力の見た目は埋めても埋めなくても同じ**なので読者に気づけない。

ハウス分割の選択肢は**置かなかった**。Placidus と Whole Sign はカスプで割れるが
**アセンダントは同一**で、カスプはここで使っていない。何も変えない選択肢を出すのは、
出さないより悪い。

**数秘術** — 薄い。そう書いてある。ここだけ空を見ておらず、
**日付の書き方**（十進・グレゴリオ暦・時刻も場所も無視）に乗っている。
答えは9通りなので**1行がおよそ9人に1人に当たる**（実測11.2%。宿曜の1宿は3.7%、
命式は桁が3つ違う）。入れたのは、上に書いた較正のためである。

### 緯度が戻ってきた

「使っていないのに必須」で外した入力である。アセンダントが本当に要るので戻したが、
**何に使うのかを欄に書いた**——外した理由がそれだったので。命式・九星・宿曜・数秘術には
一切効かない。空でよく、その場合アセンダントだけが出ない。

検算も書き換えた。前は「緯度はどこにも無い」だったが、それは何も使っていなかった頃の
言い方である。いまは**「使うページだけが、使い道を書いた上で訊く」**——
訊いていないページに文字列が残っていても落ちるし、訊いているのに欄が
「アセンダント」と書いていなくても落ちる。

緯度と経度を**取り違えると、もっともらしいアセンダントが2星座ぶんずれて出る**
（岩見沢で 300.6° → 243.8°）。エラーは出ない。なので検算は ARMC から古典式で
計算し直して照合する（一致は 1e-13 度）。

## 時の欄 — 同じ問いを4つの倍率で

10年（大運）／今年／今月／今日を1本の列に並べる。問いはどれも同じ——
**巡ってきているのは、この盤が必要とする五行か、消耗する五行か。**

並べることが本体である。**追い風の10年の中の悪い日**と、**向かい風の10年の中の
悪い日**は別の事実で、並べないと自分がどちらにいるか分からない。

> 今日は木の日で、あなたには**向かい風**です。
> ただ、上の段もそろって向かい風です。今日だけの問題ではないので、
> 今日の不調を今日のせいにしないほうがいいです。長い向かい風の中の一日です。

「今」の四柱も命式と同じ engine で立てる。年は立春で、月は節入りで切り替わる。
**日運を暦の月日で計算したら、年に十数回、自分の命式と矛盾する。**

## 蔵干 — 支の中に隠れている干

地支は一つの五行ではない。寅は名目上は木だが、甲（本気）・丙（中気）・戊（余気）を
抱えている。名目の五行だけ数えるのは、そこにあるものの一部しか数えていない。

**流派を一つ選んで黙って使うのではなく、両方計算して割れたら言う。**
仕様§4が定気/恒気に与えているのと同じ扱いにした。

### 表を構造で検算する

手で書いた表なので、信じずに**2つの構造規則から再導出して照合**している。

- **余気＝前の支の本気**。丑は子を受けて癸、卯は寅を受けて甲、午は巳を受けて丙。
  例外なく12支すべて（亥→子で一周する）
- **中気＝三合局の相手**。寅午戌は火に集まるので寅は丙、戌は丁。申子辰は水、
  亥卯未は木、巳酉丑は金。四正のうち子卯酉には中気が無い（午だけは己を持つ例外）

**この検算が実際に誤りを捕まえた。** 戌の中気と余気を入れ替えて書いていた
（正しくは 中気丁・余気辛）。表のtypoは黙って全ての判定を曲げるので、
構造から照合していなければ気づけなかった。

各支の重みは合計1に正規化してあるので、蔵干を入れても点数のスケールが変わらず、
2つの計算を直接比べられる。

## 大運 — 「いつ」が言えるようになる

ここまでは固定した盤の話だった。大運は、それを時間軸に載せる。
**必要な五行が実際にどの10年で巡ってくるか**、どの10年が逆風か。
四柱推命が判断に使われる理由の中心はここにある。

- **向き**: 陽男陰女は順行、陰男陽女は逆行。これが性別を要求する唯一の理由で、
  そう明記したうえで「答えない」も選べる（選ばなければ大運だけ出ない）
- **立運**: 順行なら生まれてから次の節入りまで、逆行なら前の節入りから生まれた時まで。
  その日数を3で割る（3日＝1年、余り1日＝4ヶ月）。**元の日数も画面に出す** —
  流派が争っているのはその丸め方だから
- 節入りの瞬間は月柱と同じ engine から取るので、§2の27分は既に入っている

出力は10年ごとの帯で、各期が追い風か向かい風かを色で示し、現在地を印す。

> いまは27〜37歳の乙酉。向かい風の10年です。
> 次に追い風の10年が来るのは**57歳から**（戊子・土）。21年先です。

## 名前も見る（姓名判断）

四柱推命と姓名判断は別の体系なので、混ぜて一つの結論にはしない。
ただし**両方とも五行を語る**——ここが唯一、正当につながる場所である。

命式はすでに「その人に効く五行（用神）」を出している。だから名前に聞ける問いは
一つに絞れる: **あなたの名前は、命式が足りないものを補っているか？**

### 画数の出典

**KANJIDIC2**（EDRDG, CC BY-SA 4.0）の `<stroke_count>`。日本の漢字辞典の数え方。

Unihan の `kTotalStrokes` は使わなかった。中国字形に従うため、辶 と 阝 を含む字で
日本の慣行とずれる。**郎 を8画とする**（辞典は9画）——日本人の名前で最頻の字の一つで、
ここを外すのは致命的だった。既知19字で照合して Unihan 19/21、KANJIDIC2 21/21。

濁点・半濁点は NFD 分解して +2 / +1。画数が引けない文字は0扱いにせず、
「読めなかった字」として画面に出す。

### 入れなかったもの

**81画の吉凶表**。市販の姓名判断の中心だが、流派差が大きく、黙って載せると
流派を一つ選んで隠すことになる。実測できる根拠も無い。入れるなら、天体暦や
万年暦と同じように出典を名指しして入れる。

## 仕様からの逸脱（作者承認済み）

v2仕様 §5 は「参照するのは占いアプリではなく紙の万年暦」「動きは27分トグルに
だけ使う」と定めている。見た目を占いらしく強くする方針に切り替えたため、
以下を意図的に上書きしている。**盤の計算内容は一切変えていない。**

| 仕様 | 現状 | 理由 |
|---|---|---|
| 万年暦の緊張感を素材にする | 羅盤＋星空 | 見た目の方針変更。判断は借りていない |
| 動きは27分トグルにだけ | 針の掃引・登場・星の瞬き | 同上。`prefers-reduced-motion` は全て尊重 |
| 五行五色をそのまま使う | 実測で再ステップ | 元の色は暗い地色上で判別不能だった（下記） |
| §8「人物評を出さない」 | 盤のページでは厳守。語りは別ページに分離 | 作者の依頼。混ぜず、確からしさの違いを明示した |

一方、次の骨は仕様どおり残している。朱は節入り時刻専用。五色は大面積に
使わない。誤差棒の3状態。分岐軸を隠さない。出典の無い記述を書かない。

### 五行の色を実測で作り直した理由

仕様の五色をマーク色に使うと、計測上こうなる:

- 木 `#2E5E4E` と 火 `#A8322D` が protanopia で **ΔE 5.6** しか離れない
- 水 `#1C2430` は地色そのもので **コントラスト 1.12** — 不可視

五行の読みは保ったまま再ステップし、CVD分離 8.6 / 通常視 16.0 /
全スロット 3:1 以上を通した。金が無彩色寄りなのは金の意味そのもので、
識別は常に隣の干支文字が担っている。

## 立っているもの

- **真太陽時**を実際に計算する。地方時差（岩見沢で +27分）と均時差（最大 ±16分）を、
  Swiss Ephemeris の `swe_time_equ` から取る。近似式は書いていない
- **節入りは UT で判定する。** 年柱・月柱に地方時差を掛けない。掛けると27分ぶん狂う
- **誤差棒を持つ。** 出生時刻の確からしさを入力し、境界をまたぐときは両方の命式を並べる
- **流派で割れる軸を隠さない。** 12通りを内部で全て計算し、実際に分岐する軸だけを開く
- **外部に何も送らない。** 天体暦は同梱。読み込み後の通信はゼロ。保存もしない

静的ファイルなので、HTTP で配れば動く。`file://` では WebAssembly を読めない。

```
python3 -m http.server 8000
```

## 精査で見つけて直したもの

MBTI 式の伝え方を入れたあと、穴とバグを探して10件見つけた。実測で裏を取ったものだけ
書く。重かったのは「もっともらしく見えて中身が無い」種類。

**画数が1文字も引けない名前に、断定を返していた。** `Smith / John` を入れると五格が
すべて 0画 になり、`elementOfCount(0)` がそれを素直に「水」と読んで、
「名前は足りないものを補う側には回っていない」と言い切っていた。出典チップには
`人格:0画` `element:水` と出るので、**形式上は出典付きに見えて中身が空**——出典チップ
機構が防ぐはずだった失敗そのもの。いまは姓か名の既知文字が0なら節ごと出さない。
人格は姓の末字と名の頭字の2文字だけで決まるので、その2文字が引けないときも出さない。

**時の欄が自分と矛盾していた。** 「今日は**向かい風**です。特に押しも引きもない日です。」
今日が向かい風で上の段が同数のとき、分岐が抜けて中庸用の文に落ちていた。3,000命式で
1.0%。いまは54通りの組み合わせを全部掃いて検算している。

**`speak()` の中に「いま」が2つあった。** 年運は引数の `nowJdUt` を見て、時の欄は
`new Date()` を見ていた。2030年を渡すと年運だけ動いて今日の行は動かない。これは
2文が食い違うだけでは済まず、**`today:*` の頻度が生成した日の実時計に依存する**ため、
「20,000人ぶんを実際に数えた」がそのキーについて再現できなくなっていた。いまは一つの
「いま」が全体を動かし、頻度表には**数えた日付が刻印される**（`RARITY_COUNTED_ON`）。
`node tools/build-rarity.mjs 20000 2026-07-30` で再現できる。

**出典チップと注意書きが WCAG AA 未達だった。** `--ink-faint` #626C7C は背景の上で
3.69:1、オーロラの上で **3.23:1**（10〜11.5px の文字に必要なのは 4.5:1）。使用箇所26、
その中に `.cite`（**出典チップ全部**）と `.hint`（**注意書き全部**）。いちばん読みにくい
文字がいちばん正直さを担っているのは逆立ちしている。色相を保ったまま #7A869A に上げて
5.32:1 / 4.65:1。コントラストは `verify.mjs` が CSS から読んで計算で検算する。

**盤ページと語りページが違う命式を出しうる。** 盤の真太陽時トグルを切ると、4,000命式で
**40.9%** が別の命式になり、**8.5%** が別の判定、**11.7%** が別の用神になる。どちらの
ページもそれを言っていなかった。いまは補正を切ると盤のフッターに注意が出て、語りページは
「真太陽時で読んでいます」と明示する。

**未来の生年月日を受け付けていた。** 1929を2029と打つと年齢が −5歳 になり、大運の行が
黙って消えて、残りは普通に描画されるので**壊れていることが画面から分からない**。いまは
`max` を今日に切り下げ、その裏で JS も弾く（`max` を外しても弾けることを検算している）。

**使っていない緯度を必須で訊いていた。** 真太陽時のずれは経度だけで決まるので、緯度は
命式に一切効かない。保存も送信もしないアプリに「記録として受け取る」入力欄が要る理由は
無い。外した。

ほかに、JS の例外文がそのまま日本語UIに出ていたのを日本語の文に（詳細はコンソールへ）、
`cycleAtAge` が壊れた引数で落ちるのを null 返しに、弁別率の指標そのものを差し替えた
（上の「反バーナムの計測」）。

**標本抽出器が壊れていた。これがこのリポジトリで見つけた中でいちばん重い。**

このアプリの主張は「実測している」の一点に乗っている。「◯人に1人」のチップも、
バーナム文を弾いた 70% の線も、組み合わせ数も、全部ひとつの乱数から引いた標本の上に
建っていた。その乱数がこれ:

```js
seed = (seed * 1103515245 + 12345) & 0x7fffffff;
```

C の教科書の LCG で、C では正しい。**JavaScript では壊れる。** `seed` は 2^31 まで
行くので、`seed * 1103515245` は約 2.4×10^18 ——倍精度が連続する整数を表せなくなる
2^53 のはるか先である。掛け算の下位ビットは丸め誤差になり、`& 0x7fffffff` が
残すのはまさにその丸め誤差だった。弱い乱数ではなく、**乱数ではなかった**。

`build-rarity.mjs` が実際に使っていた呼び出し方で測ると:

- **3月・4月・7月・8月・11月・12月が一度も出ない**
- 20,000回の抽出で、`(月, 日, 時)` の組は **161種**（可能なのは 8,064種）

つまり頻度表は、**春と秋が存在しない標本**で測られていた。読者に「これはあなただけの
話ではありませんよ」と示すために出していた数字が、全部ちがう問いに答えていた。

直したあと（`tools/random.mjs`・mulberry32、掛け算は `Math.imul` で32ビットに収める）
再測すると、**36件の文が「一度も測れていなかった」状態から出てきた**——頻度が無い文は
チップが黙って消えるので、それらは読者に何も示さずに出ていたことになる。
33件が5ポイント以上動き、最大は 66.2% → 51.9%。

副産物として、**70% のバーナム線を検算の門に入れた**。これまで
`reading-metrics.mjs` が「<- Barnum risk」と印字するだけで、誰かが出力を読むかどうかに
懸かっていた——通根の 90% の文が手作業で見つかるまで生き延びたのはそのためである。
門にできなかった理由もはっきりしていて、**判定に使う頻度そのものが壊れた標本から
出ていた**からだ。いまは 645文の最頻が 64.4% で、門が閉まる。

**検算がページの一覧を手書きで持っていた。** これは3ページ目を足したときに出た。
`verify.mjs` の4箇所が `['index.html', 'voice.html']` と
`['app/main.js', 'app/voice-main.js']` を**それぞれ書き写して**持っていて、
託宣ページの追加で4箇所が同時に壊れた。壊れ方は2種類で、**後者のほうが悪い**:

- 1件は**落ちた**。未参照CSSの走査が `oracle-main.js` を読まないので、
  託宣ページで**生きている8クラスを死んだと報告**した
- 残り3件は**通った**。新しいページを一度も見ないまま緑になった。
  何も測っていない検算が緑を出すのは、赤い誤検知より質が悪い

落ちたほうの検算は、コメントに「生きたクラスを死んだと報告すると全員がこの検算を
無視するようになる」と自分で書いてある。まさにそれをやった。

直し方は「託宣を4箇所に書き足す」ではない。**一覧をリポジトリから導出する**——
ルートの `*.html` がページで、入口スクリプトは**各ページが自分の `<script>` タグで
名乗る**。4箇所に表を写すのは4箇所を同期し続けるという約束で、この約束は既に
一度破られた。いまは `oracle.html` を退けるとページ数が 3→2 に動く（実際に確かめた）。

**探して問題が無かったもの**も書いておく: HTML注入の経路（`el()` は `textContent`、
`innerHTML` の1箇所は補間なしの静的文字列）、蔵干の配分合計（全12支で1.000）、
1800年と2399年の両端、閏日、1948〜51年の夏時刻、時刻不明の三柱、経度や時刻が NaN の
とき、名前の前後空白・濁点・サロゲートペア・かな。託宣ページの未来日付防御と
場所欄（`japanNow` も `attachPlaceField` も他の2ページと同じく入っていた——
上の3件の見逃しは、いまのところ空振りだった）。

## 図

語りページには図が一つも無く、天盤は盤ページにしか無かった。読者が実際に読むのは
語りページのほうなので、そこに3つ作った。

**命式の図**（`app/ui/board.js`）。`庚午 壬午 辛亥 辛卯` という文字列だったものを、
鑑定紙と同じ4列の盤にした。干の下に支、その脇に通変星、いちばん下に蔵干、
柱ごとの担当（生まれと親／仕事と社会／あなた自身／晩年と体）。

**五行のめぐり**（`app/ui/wuxing.js`）。木火土金水を五角形に置き、**外周に相生の輪、
内側に相剋の星**を引く。相生の順に時計回りへ並べると、一つ飛ばしに結んだ線が相剋の
星になる——だからこの並びで描く。節点の**面積**が数（半径ではない。倍を倍に見せるため）、
欠けは中空の輪、用神には輪の印。

**大運と流年の帯**（`app/ui/luckband.js`）。10年ごとの一覧だった大運を、
**その中の一年ごとに割った**。人生は10年刻みでは来ないし、伝統もそう読まない——
大運の中に流年があって、読みはその組み合わせ。開いた瞬間は「いま」の位置まで
スクロールした状態で出る。

### 色は測って決めた（配色の検証を通した結果、設計が変わった）

追い風／向かい風に緑と赤を当てるつもりだったが、検証にかけたら
**木（緑）と火（赤）との差が ΔE 4.4**——判定の下限15を大きく割っていて、
色覚が正常な人でも見分けられない。5色を五行の**識別**に使っている以上、
6色目と7色目は原理的に衝突する。

なので**極性には色を使わない**ことにした。追い風は中心線より上、向かい風は下——
位置というより強いチャンネルを、いちばん大事な情報に充てた。五行の色は識別だけに残す。

最初の版では帯の棒に五行の色を載せていて、これも捨てた。**赤い棒が並ぶと、
誰が見ても「悪い年が続く」に見える**。凡例に何と書いてあっても、広い面積の
カテゴリ色は状態として読まれる。棒は一色にした。

同じ理由で、色は一度も単独の手がかりにしていない。五角形の節点には必ず五行の名が
入り、盤では色が乗るのは**干支の文字そのもの**（文字がデータなので）で、
まわりのラベルは全部テキスト色。

### 動き

相生の輪と相剋の星が順に描き起こされ、帯のマスが立ち上がり、盤が柱ごとに現れる。
ライブラリは使っていない。**動きは常に追加情報で、止まった状態でも図は完全に読める。**
`prefers-reduced-motion` で全部止まる（止めた状態でも検算している）。

途中で一つ壊した: 相剋の破線を `stroke-dasharray` のアニメーションで描き起こしたら、
**破線の模様ごと上書きされて実線で終わっていた**。生の輪と見分けがつかなくなるので、
剋の線はフェードで出すようにした。ブラウザ監査がこれを見張っている。

## ホーム画面に置く（PWA）

ホーム画面に追加してページを切り替えると Safari に戻ってしまう、という不具合が
あった。**原因はマニフェストが無かったこと。** iOS はスコープを知らないので、
フッターのリンクを踏んだ時点で「アプリの外」と判断していた。

- `manifest.webmanifest` — `scope` と `start_url` は **相対（`./`）**。GitHub Pages は
  サブパス配信なので、絶対パスの `/` にするとサイト全体がアプリの外になる
- アイコン一式（以前は1枚も無く、ホーム画面のアイコンはページのスクショだった）。
  絵柄は天盤と同じ 羅盤 の語彙で、`tools/build-icons.mjs` が同梱の Chromium で
  ラスタライズする。PNG は生成物としてコミットする（`strokes.js`・`rarity.js` と同じ扱い）
- `apple-touch-icon` と `apple-mobile-web-app-*`。iOS はステータスバーと名前について
  マニフェストではなくこちらを読む
- **Service Worker でオフライン動作**。app shell と天体暦（`.se1` は `swisseph.data` に
  同梱されている）を含む38ファイル・3.44MB を先読みする

**先読み一覧は手で書かない。** モジュールを1つ足して worker を再生成し忘れると、
オフラインで白画面になる——「入れられない」より悪い壊れ方をする。`tools/build-sw.mjs` が
ディスク上の実ファイルから一覧を作り、`verify.mjs` が作り直して突き合わせる。
版は中身のハッシュなので、再生成漏れも検出できる。

**「初回ロード後は通信ゼロ」は弱まらない。** worker が返すのは同一オリジンの、
既に持っているバイトだけ。むしろ強くなる——**2回目以降の表示はネットワーク要求が
実測0件**になった。検算も主張に合わせて書き直した:
外部オリジンへの要求は常にゼロ／どの要求にも入力値が乗らない／同一オリジンの
通信はアプリ自身のファイルだけ。

## 生まれた場所（制約を読み直した）

仕様は都市名検索を禁じていた。理由は「ジオコーディング通信が発生して
『送信ゼロ』が崩れる」。**この理由は正しく、結論だけが広すぎた。**

制約が本当に禁じていたのは *ジオコーディング*、つまり**場所を他人に尋ねること**
であって、*地名* そのものではない。市区町村の表を**同梱**すれば、引くのは
端末の中で終わる。要求は0件のまま——これは主張ではなく、
ブラウザ監査で**実測している**（場所を引いたあとのネットワーク要求 0件）。

それまでの唯一の入口は十進の経度だった。これは実際の壁で、占われるには
一度ページを離れて地図を探し、数字を読んで戻ってくる必要があった。

`tools/build-places.mjs` が **1,886件**の市区町村（都道府県・市区町村・カナ・
経度・緯度）を `app/engine/places.js` に焼く。ひらがなで打っても引ける——
電話でそう打つ人がいるので、カタカナ表に寄せて照合する。

**数字は画面に残す。** 場所の欄は経度を*埋める*だけで、*隠さない*。
141.79 と直接打ちたい人はそのまま打てるし、選んだ場所がどの値になったのかは
常に見える。このアプリ全体の規則——**計算過程を見せる**——と同じ扱いにした。

この欄は**後付けで壊れないように**書いてある。マークアップは素の経度欄のままで、
モジュールが動かなくてもフォームは完全に使える。

**ここで無言の事故を1件出した。** 表の経度は小数3桁（`141.763`）だが、入力欄は
`step="0.01"` だった。埋めた瞬間に値が「不正」になり、**ブラウザは何も言わずに
送信を拒否する**——ボタンが黙って効かなくなる。`step="any"` に直し、
書き込んだ値が受け付けられなければ**理由を表示する**ようにした。
検算にも入れてある（3ページとも `step=any`）。

伝え方の層にも同じ門を掛けている（2,000命式を掃いて検算）:

- 目盛り4本が 0〜100 に収まる

### ブラウザ側の検算

`verify.mjs` が机上の計算を見るのに対し、こちらは**実際のエンジンが CSS を解釈して
モジュールを走らせてレイアウトを組んで通信した後にしか成り立たないこと**を測る。

```
node tools/audit-browser.mjs
```

自前でサーバを立てるので、事前に何かを起動しておく必要はない。**配信は
`/Uranaiii/` というサブパスの下で行う**——GitHub Pages がそうだからで、
ルート直下でしか成り立たないマニフェストのスコープや Service Worker の登録は、
ルートで測ると通ってしまい本番で壊れる。出荷される形で測るのが目的。

- 外部オリジンへの要求ゼロ／どの要求にも入力値が乗らない／同一オリジンの通信は
  アプリ自身のファイルだけ
- localStorage・sessionStorage・cookie がゼロ
- 320px・375px・768px で横あふれなし。**横スクロール領域の中身は除外する**——
  大運の帯は自分の箱の中でスクロールしてよく、あってはならないのは*ページ*が
  横に動くこと（ここは一度取り違えて誤検知を出した）
- `prefers-reduced-motion` の有無どちらでも成立
- 時刻なし（三柱）・性別なし（大運なし）でも図が崩れず例外も出ない
- 未来の日付を `max` 属性と JS の両方で弾く（属性を外しても弾けることを確かめる）
- Service Worker が有効化し、先読みが揃い、**通信を切っても各ページが計算まで通り、
  ページ間を移動できる**。2回目の表示はネットワーク要求ゼロ
- 図: 命式が4列そろう／五行の5節点すべてに名前がある／相剋の線が破線のまま／
  帯の棒に五行の色が乗っていない／帯の全マスに読み上げラベルがある
- 生まれた場所を引いても**ネットワーク要求は0件**。引いた経度でそのまま占える
- 託宣ページが3ページとも同じ入力で成立し、根拠の畳みが開く

**この一式は長いあいだリポジトリの外にあった。** 動いてはいたが、それは1台の
マシンでの話で、他人には回せなかった——「ブラウザ監査が見張っている」と書きながら
実体が無い状態だった。**誰も回せない検算は検算ではない**ので、取り込んだ。

playwright が無い環境では**理由を出して skip し、失敗にはしない**。検算の門は
`verify.mjs` のままで、ブラウザが無いことはアプリの欠陥ではない。

取り込んだ直後に、この監査は自分で一件見つけた: 時刻なしの命式で図の列だけ
構造が違っていて、**時刻ありでしか通らない検算になっていた**（32/33）。直して 33/33。
その後、託宣ページと生まれた場所の分を足して **54項目**。
